# 翻译工序

一篇长英文原文，拆成几部分陆续发出。这份文档写的是**流程**，不是文风 ——
怎么措辞是你的事。

## 0. 先解决授权

这一步在动手翻译之前，不在发布之前。

翻译权属于原作者。没有许可的整篇翻译就是未经授权的改编，
哪怕注明了出处、哪怕不收钱、哪怕加了大量注解，都不改变这一点。

常见的几种情况：

| 原文的授权状态 | 能做什么 |
| --- | --- |
| 明确的 CC BY / CC BY-SA 等允许改编的协议 | 可以译，按协议要求署名、并用同样协议发布译文 |
| CC BY-**ND**（禁止演绎） | **不能**发布译文。翻译就是演绎 |
| 版权所有、无声明 | 先发邮件问。得到书面同意再动手 |
| 作者已明确拒绝 | 到此为止 |

拿不到授权但仍想介绍这篇文章，退一步的做法是**写一篇自己的解读**：
用你自己的话概述、评论、补充，正文里链回原文，引用控制在必要的短句。
这是评论而不是翻译，性质不同。

问授权的信不用长。说清你是谁、想译哪篇、发在哪里、会怎么署名，
说明是非商业的个人博客，问一句是否可以 —— 大多数作者回得很快。
把回信留档，`source.note` 里写上「已获原作者邮件授权」。

## 1. 决定怎么分

**按原文的结构切，不按字数切。** 原文的大标题（`##`）就是天然的接缝，
一部分收在一个完整的意思上，别断在半句话中间。

一部分 2000–4000 汉字比较舒服，读完大约十分钟。超过这个长度，
手机上滚动条会让人望而生畏 —— 这正是分部分的初衷。

部分数量不用提前定死。目录是数文件数出来的，中途多出一部分不会有问题。

## 2. 建文件

```bash
cd scifi-blog
cp "src/content/posts/_模板-翻译系列.md" src/content/posts/dyson-sphere-1.md
npm run uid   # 输出替换掉模板里的 uid: TODO
```

**文件名决定 URL**，用英文小写短横线。文件名一旦发出去就别再改 ——
改了 URL 就变，外链和收藏全断。（uid 不受影响，它就是为此存在的。）

frontmatter 里和连载相关的两块：

```yaml
series:
  name: 戴森球的工程学 # 同系列每篇必须一字不差
  part: 2 # 阅读顺序，不是发布顺序
source:
  title: The Engineering of Dyson Spheres
  author: Jane Roe
  url: https://example.com/dyson
  note: 已获原作者邮件授权翻译。
```

几个容易踩的点：

- `series.name` 是手打的中文，**打错一个字就成了另一个系列**。
  `npm run check:posts` 每次都会列出系列清单，凭空多出一个只有一部分的系列，
  基本就是笔误。
- `part` 决定阅读顺序，**与发布时间无关**。可以先发第 1 部分，
  两周后补第 2 部分，目录顺序始终正确。
- 跳号是允许的（1、2、4）。「下一部分」找的是「排在后面的第一篇」，
  不是「part + 1」，所以预留号码不会断链。
- `series` 必须写成上面这种分行形状。行内写法 `series: { … }` 虽然是合法 YAML，
  但校验脚本只认分行的，见到别的会直接报错，不会悄悄跳过。

## 3. 译文与注解

页面上会自动出现的东西，正文里不用重复写：

- 顶部：原文出处（来自 `source`）
- 顶部：本系列目录，当前这篇高亮，其余可点
- 底部：「下一部分」链接
- 列表和首页上：`系列名 · 第 N 部分` 的小字

所以正文**不要**写「本文是《……》系列的第二部分」「下一部分请见……」——
那是页面的职责，写进正文只会在改动时变成过期信息。

注解和译文要能一眼分开。用 callout：

```markdown
> [!note] 译注
> 补背景、连相关文章、指出原文哪里是推测而不是定论。

> [!quote] 原文
> 需要逐字对照的句子放这里 —— 翻译上拿不准，或者措辞本身就是争议点。
```

术语第一次出现时把原文附在括号里：戴森球（Dyson sphere）。之后只用中文。

配图走外链，不进仓库，见 [图片工作流.md](图片工作流.md)。
**转载原文配图前单独确认许可** —— 文章的授权和插图的授权常常不是一回事，
插图往往另有版权方。拿不准就自己画，或者只留链接指回原图。

## 4. 发布

```bash
npm run check:posts   # 跨文件校验：uid 撞没撞、同系列 part 撞没撞
npm run build         # build 第一步就是上面这条，撞了会直接停下
npm run dev           # 本地看效果
```

写完一部分就把 `draft: true` 删掉。

**注意 `draft: true` 在本地也看不到。** `postFilter` 是无条件排除草稿的，
`npm run dev` 里同样不显示，页面压根不会生成。想在本地预览就得先把这行删掉 ——
反正没构建、没推送，就不会出现在线上。

还有：`pubDatetime` 只要比**当前时刻**晚，生产构建就不会生成这个页面。
写「今天晚上 9 点」这种看着无害的时间，如果构建发生在那之前，
文章就悄悄地不存在 —— 不报错，只是页面没了。要么写已经过去的时间，
要么记得到点后重新构建。

### 关于定时发布

`pubDatetime` 填未来的时间，这篇在生产环境就不会显示 —— 看起来很适合
「一次写完三部分、排好档期自动放出」。

**但静态站不会自己到点更新。** 页面是构建那一刻生成的，
Cloudflare Pages 不会因为时间到了就重新构建。排了档期而不重新构建，
那篇永远不会出现。

要真正用上定时发布，得让构建按时触发 —— Cloudflare 的 Deploy Hook
加一个定时任务（Cron Trigger 或任何能定时发 HTTP 请求的地方），
每天跑一次。没配这个之前，就当没有定时功能：写完、构建、发布。

## 5. 想改叫法

「第 N 部分」这个说法定义在 `src/i18n/lang/zh.ts` 的 `post.partLabel`。
想用「（上）（中）（下）」或者「第 N 篇」，改那一行就行 —— 但注意
`partLabel` 是按数字套模板的，上中下这类固定叫法只适合恰好三部分的系列。
